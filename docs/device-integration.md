# 设备侧接入指南

换产品、换广播名，**只改 `src/config.ts`**

---

## 1. 协议速查表

手机（BLE 中心设备）↔ 产品（BLE 外围设备），走一个自定义 GATT 服务。

| 环节       | 约定                                                                                                                                                                                       |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 广播名     | 以固定前缀开头，默认 `CS-`，建议后面接设备 MAC 后 3 字节（如 `CS-A1B2C3`），方便用户在多台设备间区分                                                                                   |
| 广播内容   | 建议**同时**带上 Service Data（AD type `0x16`，内容是 16 位 UUID `0xFF00`）和厂商自定义数据（AD type `0xFF`，前两字节是厂商 ID）。这样即使某些手机拿不到广播名，也能被识别出来 |
| 服务 UUID  | `0xFF00`（16 位）                                                                                                                                                                        |
| 写特征     | `0xFF01`，属性 `WRITE_REQ` + `READ` —— 注意是**带响应写**                                                                                                                    |
| 通知特征   | `0xFF02`，属性 `NOTIFY` + `READ`，必须带 CCCD 描述符                                                                                                                                 |
| 特征值长度 | 建议写特征和通知特征的值上限都给到 512 字节                                                                                                                                                |
| 数据编码   | 一律 UTF-8，内容为 JSON                                                                                                                                                                    |

### 数据格式

**手机 → 设备**（写 `0xFF01`）：配网信息

```json
{"ssid":"WiFi名称","pwd":"WiFi密码","city":"深圳市","district":"南山区"}
```

**设备 → 手机**（通知 `0xFF02`）：Wi-Fi 扫描结果

```json
[{"name":"WiFi名称1"},{"name":"WiFi名称2"}]
```

**设备 → 手机**（通知 `0xFF02`）：配网结果

```json
{"state":"success"}
```

```json
{"state":"fail"}
```

### 交互时序

```
手机连接设备
   ↓
手机打开通知（底层写 CCCD = 0x0001）
   ↑ 这一步同时就是「开始扫描 Wi-Fi」的命令
   ↓
设备扫描 Wi-Fi，把列表通过通知推给手机
   ↓
用户选网络、输密码、选城市 → 手机把配网信息写到 0xFF01
   ↓
设备连接路由器 → 通过通知回报成功 / 失败
```

## 2. 接入步骤

### 2.1 广播

开一个可连接、可扫描的传统广播（LEGACY ADV），载荷里放：

1. Flags（`0x06`）
2. 本地名（AD type `0x09`）：`CS-` + MAC 后 3 字节，大写十六进制
3. Service Data（AD type `0x16`）：**两个字节 `00 FF`**

   > 注意字节序：蓝牙 UUID 按小端传，所以 `0xFF00` 在空口上是 `00 FF`，不是 `FF 00`。
   > 这个很容易写反，写反了手机还能靠广播名匹配上，但一旦用户设备名不同就漏了。
   >
4. 厂商自定义数据（AD type `0xFF`）：厂商 ID，小端两字节

设备名和 UUID 都通过 `src/config.ts` 配置，改成别的名字时小程序侧同步改一下即可。

### 2.2 GATT 服务

建一个服务 `0xFF00`，里面两个特征：

```
服务 0xFF00
├── 特征 0xFF01  WRITE_REQ | READ      值上限 512
└── 特征 0xFF02  NOTIFY | READ | WRITE_REQ + CCCD   值上限 512
```

建议在手机的 MTU 协商请求里回一个较大的值（比如 512）。手机侧会：

- 能协商就协商到 512；
- 协商不到（iOS 常见，通常只有 185）就按实际值分包；
- 连 MTU 都拿不到时按 BLE 规范最小值 23 兜底（每包 20 字节）。

### 2.3 收配网信息（写 0xFF01）

设备收到写入后：

1. **按长度累积**到缓冲区里（不要假设「一次写 = 一条完整 JSON」）；
2. 累积到能 `parse` 成功再处理，成功后清空缓冲区；
3. 解析出 `ssid` / `pwd` / `city` / `district` 四个字段。

`city` / `district` 是可选的：小程序一定会在用户选了城市之后下发，但做成可选更稳（兼容老版本小程序）。

参考写法：

```c
static char     s_json_buf[512];
static uint16_t s_json_len = 0;
static uint32_t s_json_last_ms = 0;

/* 收到写事件 */
{
    /* 1) 长时间没有新分片，把上一轮的残包丢掉，避免两次配网串在一起 */
    if (s_json_len > 0 && (now_ms() - s_json_last_ms) > 3000) {
        s_json_len = 0;
    }
    s_json_last_ms = now_ms();

    /* 2) 溢出保护：宁可丢掉重来，也不要越界写 */
    if (s_json_len + len >= sizeof(s_json_buf)) {
        s_json_len = 0;
    }

    /* 3) 按实际长度拷贝（写入缓冲不一定以 '\0' 结尾，不能当字符串用） */
    memcpy(s_json_buf + s_json_len, value, len);
    s_json_len += len;
    s_json_buf[s_json_len] = '\0';

    /* 4) 解析成功才算收全；失败说明还差后面的分片 */
    if (parse_json(s_json_buf) == NULL) {
        return;                 /* 继续等下一片 */
    }
    s_json_len = 0;             /* 只有收全了才清空 */

    /* ... 取 ssid / pwd / city / district ... */
}
```

### 2.4 推 Wi-Fi 列表（通知 0xFF02）

手机打开通知的那一刻（写 CCCD = `0x0001`）就是「开始扫描」的命令，扫描完成后把结果推上去：

- 用 JSON 数组，每条至少带 `name`（SSID 名）；
- 按信号强度从强到弱排序，用户先看到最可能连的那个；
- 跳过空 SSID（隐藏热点）和重复 SSID；
- 总长度控制在 500 字节以内（超过就截断，见 3.2 节的分包说明）。

### 2.5 回报结果（通知 0xFF02）

连上路由器并拿到 IP 后通知 `{"state":"success"}`，失败则 `{"state":"fail"}`。

**报完成功不要立刻断开蓝牙**，见 3.6 节。

## 3. 常见错误与坑

### 3.1 写特征必须处理分包：一次写 ≠ 一条完整 JSON

配网 JSON 的长度 = SSID（最多 32 字节）+ 密码（最多 63 字节）+ 城市 + 区县，
很容易超过 100 字节，而单次可写长度受 ATT MTU 限制：

| 手机               | MTU                  | 单包可写          |
| ------------------ | -------------------- | ----------------- |
| 安卓 + 微信小程序  | 可协商到 512         | 最多 509 字节     |
| iOS + 微信小程序   | 由系统协商，通常 185 | 最多 182 字节     |
| 兜底（拿不到 MTU） | 23                   | **20 字节** |

所以手机侧**一定会分包写**（按 `MTU - 3` 切片、串行发送、片间留几十毫秒）。

**典型错误**：收到写事件就整包解析。

```c
{ /* 错误示范 */
    json_t *root = parse_json(value);   /* 只对第一个分片有效 */
    if (root == NULL) { log("parse failed"); return; }
}
```

结果是：每个分片各自解析失败，全部被丢弃，**设备永远收不到配置**，而日志里只会反复出现
「解析失败」，看起来像是数据格式问题。

**正确做法**：按长度累积，解析成功才清空（见 2.3 节的参考写法）。

### 3.2 通知报文可能超过单包 MTU，设备侧要分包发

Wi-Fi 列表最长可到 500 字节，而 iOS 的 MTU 通常只有 185 —— 一次发不完。
手机侧已经实现了分片重组（按字节流拼接 → 按 UTF-8 边界解码 → 按括号配平提取完整 JSON），
所以设备侧分批发是安全的，但有两条硬要求：

1. **必须顺序发送**，中间不要插入其它通知（尤其是状态通知），否则两段数据会串在一起；
2. **分片之间留一点间隔**（比如 20ms），避免协议栈丢包。

```c
/* 协商成功后记下 MTU */
static uint16_t s_mtu = 23;
/* MTU 变化回调里: s_mtu = 新的 mtu; */

uint16_t chunk = (s_mtu > 3) ? (s_mtu - 3) : 20;
uint16_t len   = strlen(text);
for (uint16_t off = 0; off < len; off += chunk) {
    uint16_t n = (len - off > chunk) ? chunk : (len - off);
    notify(text + off, n);
    delay_ms(20);
}
```

### 3.3 拼 JSON 必须转义，否则手机端会解析失败

SSID 里**真的可能出现** `"` 或 `\`（比如热点名叫 `My"Home"WiFi`）。
如果用手工字符串拼接、不做转义，拼出来的就是非法 JSON。

**手机端的处理是：解析失败就不派发、不猜、不吞错数据**，界面上显示「设备返回的数据看不懂」，
并在「查看设备原始报文」里把收到的原文显示出来。这是刻意的 —— 静默容忍错误数据比报错更难排查。

**正确做法**：用 JSON 库构造，不要手工拼。

```c
array = json_array_new();
for (每个 AP) {
    if (strlen(ssid) == 0) continue;        /* 隐藏热点跳过 */
    item = json_object_new();
    json_object_add_string(item, "name", ssid);   /* 库会自动转义 */
    json_array_add(array, item);
}
text = json_print_unformatted(array);
notify(text, strlen(text));
```

> 如果 JSON 库把非 ASCII 转成 `\uXXXX`，也没问题 —— 手机端 `JSON.parse` 会自动还原。

### 3.4 城市 / 区县缓冲区要留足长度

小程序会让用户选到**区县**一级，值都发全称（带「市」「区」）。全国行政区划里：

| 项目 | 最长名称                       | UTF-8 字节数      |
| ---- | ------------------------------ | ----------------- |
| 市级 | 黔西南布依族苗族自治州         | 33 字节           |
| 区级 | 内蒙古阿拉善高新技术产业开发区 | **45 字节** |

所以设备侧存城市/区县的缓冲区如果只有 24 字节，一定会截断，而且截断可能切在汉字中间，
产生非法 UTF-8，屏幕上显示乱码。

**建议**：城市和区县各留 `char[64]`（64 字节 = 21 个汉字，覆盖全部行政区划名称）。

**手机上也有兜底**：小程序按 `src/config.ts` 的 `deviceTextMaxBytes`（默认 63）校验，
遇到超长名称会提示用户「将按 XX 截断后下发」，**不会写越界**。
把设备侧缓冲区改大之后，同步把这个值改成 63。

> 另外注意：数据在固件里往往要经过好几个结构体传递（配网结构体 → 业务结构体 → UI 结构体）。
> **任何一环小了都会被静默截断**，所以这几处要一起改。

### 3.5 「重新扫描」没有独立命令，只能靠重写 CCCD 触发

协议里没有「请重新扫描 Wi-Fi」这条命令。设备只在**收到 CCCD 写 `0x0001`** 时扫描一次。

小程序的「重新扫描」是这样实现的：**关通知 → 开通知**，底层就会依次写 `0x0000` 和 `0x0001`。

**设备侧要保证**：每次收到 CCCD 写 `01 00` 都重新开始扫描。
另外，如果上一次扫描还没结束又收到一次，**不要并发起两次扫描** —— 先停掉或者直接忽略。

### 3.6 成功通知和断开之间要留时间

设备侧常见的收尾写法是：通知成功 → 释放蓝牙资源 → 断开连接。

**这两步之间要有几十毫秒的间隔**（比如 40ms），否则协议栈还没把「成功」这个包发出去，
连接就断了，手机**只看到断开、收不到成功通知**，用户会以为配网失败。

手机侧已经处理了「先收到 success，再断开」这个顺序（收到成功后就忽略随后的断开事件），
但**顺序不能反**。

### 3.7 Wi-Fi 列表带上 rssi 和加密方式

只发 SSID 名字的话，小程序列表上显示不出信号格和锁图标。手机上**已经兼容**这几种格式，
设备侧加了就自动生效，小程序一行都不用改：

```json
[
  {"name": "WiFi-A", "rssi": -45, "sec": 3},
  {"name": "WiFi-B", "rssi": -72, "sec": 0}
]
```

- `rssi`：整数 dBm（负值）。小程序按 `-55 / -65 / -75 / -85` 换算成 4 格信号。
- `sec`：`0` 表示开放网络，非 0 表示加密。小程序据此显示「加密 / 开放」标签。

字段名也做了宽容处理（`ssid` / `name`、`signal` / `level` / `rssi` 都认），但建议就用这三个。

### 3.8 配网成功后要把凭据持久化

配网只是在内存里连上了 Wi-Fi，**不落盘的话一断电就白配了**，用户得重来一次。

SSID 和密码都要存进非易失存储。有个小技巧：**SSID 最后写**，把它当作「这一对有效」的标记，
这样即使密码写成功而 SSID 写失败（或反过来），读的时候也不会拿到半对凭据。
城市和区县同理，一起存下来。

### 3.9 城市要持久化，并且优先于任何「自动定位」

如果固件里还有别的取城市途径（比如按 IP 定位、按基站定位），要保证
**配网时用户选的城市优先**，否则设备一重启就又跳回自动猜的城市，
用户在界面上选的等于白选。

### 3.10 换了广播名或 UUID，要同步改小程序配置

小程序默认按这几条识别设备（都在 `src/config.ts`）：

- 广播名前缀（默认 `['CS-']`）
- Service Data 里的 16 位 UUID（默认 `FF00`）
- 厂商 ID

匹配策略默认是「**任一命中即认为是目标设备**」，这是刻意的：部分安卓机型拿不到广播数据、
iPhone 有时拿不到完整的本地名，只用一条条件会漏设备。

改了广播名或 UUID，**必须同步改 `src/config.ts`**，否则扫不到设备。

### 3.11 用带响应写（WRITE_REQ）

协议约定写特征声明为 `WRITE_REQ`。手机侧会读特征属性并自适应 ——
如果以后改成无响应写（WRITE_COMMAND）也能跑，但**带响应写更慢**，
长报文分很多包时下发时间会明显变长。

## 4. 联调步骤

### 4.1 手机侧先自测（不需要设备）

```bash
node test/run.js        # 或 npm test；不需要 npm install，Node 直接跑 TS 源码
npm run type-check
```

**期望**：`全部通过: 413/413`。

覆盖的内容：协议编解码、UTF-8 边界、JSON 分片重组（**穷举所有切分点**）、
粘包拆包、超时丢弃、重扫时序、断开后连接态清理，以及工程结构（页面文件、
import 路径、平台隔离、构建配置）。

### 4.2 设备侧接入后，按这个顺序验证

| 步骤 | 操作                   | 期望现象                                                 | 不符时先查                         |
| ---- | ---------------------- | -------------------------------------------------------- | ---------------------------------- |
| 1    | 设备上电               | 串口打印广播已启动，广播名 `CS-xxxxxx`                 | 3.10                               |
| 2    | 打开小程序             | 自动自检蓝牙和定位权限，列表里出现该设备，标记「可配网」 | 3.10（广播名 / UUID）              |
| 3    | 点击连接               | 连接成功，进入 Wi-Fi 列表页                              | 3.11（服务 / 特征 UUID）           |
| 4    | 等待列表               | 几秒内出现设备扫到的 Wi-Fi                               | 3.5（CCCD 触发）、3.3（JSON 转义） |
| 5    | 选网络、输密码、选城市 | 结果页显示「设备正在连接路由器」                         | 3.1（分包解析）                    |

| 7    | 看设备屏幕             | 城市和区县显示正确                                       | 3.4（缓冲区长度）                  |

### 4.3 手边的排查工具

小程序内置了两处**原始报文**查看能力，固件还在调试时特别有用：

- **Wi-Fi 列表页**底部「查看设备原始报文」→ 显示设备发过来的原始 JSON
- **结果页**展开「排查信息」→ 显示协商到的 MTU、下发的报文、设备回传的报文

两边一比，就能立刻定位是设备发错了还是手机解错了。

## 6. 总结

**协议本身很简单，坑全在「长度」和「时序」上**：

- **长度**：24 字节的缓冲区装不下全国区划名；单包 20 字节装不下一条配网 JSON；
  500 字节的列表超过 iOS 的 MTU。
- **时序**：CCCD 写入才触发扫描；成功通知要在断开之前发出去；收包要先订阅再开通知。

上面 11 条里，**3.1 / 3.2 / 3.3 / 3.4 / 3.8 是必做项**，不做一定出问题；
其余是影响体验或稳定性，建议一并处理。

### 7.1 手机侧的分层

| 连接编排（扫描 / 连接 / 分包写 / 收包重组 / 重扫） | `src/ble/client.ts`             | 否，只认 `BleAdapter` 接口             |
| 平台适配器                                         | `src/ble/adapters/mp-weixin.ts` | **是，全工程唯一调 uni/wx 的地方** |
| 界面                                               | `src/pages/*.vue`               | 否                                       |

出 App 端要做的只有一件事：**再写一个实现 `BleAdapter` 接口的适配器**
（放 `src/ble/adapters/app.ts`），然后在 `src/ble/adapter.ts` 的
`#ifdef APP-PLUS` 分支里返回它。协议、编排、界面一行都不用改。

`test/structure.test.js` 里有一条断言专门守着这个约定：平台调用只允许出现在
`adapters/` 目录里。谁要是在 `client.ts` 里写了 `uni.xxx`，测试立刻会红。

### 7.2 必须提前知道的坑：uni-app 的 App 端没有 BLE 接口

uni-app 官方的 `uni.*` 蓝牙接口（`openBluetoothAdapter` / `createBLEConnection` /
`writeBLECharacteristicValue` 等）**只支持小程序端**，App 端没有对应实现。
所以 App 端必须自己解决 BLE 中心设备（Central）能力，三条路：

| 方案                             | 说明                                                           | 代价                                                           |
| -------------------------------- | -------------------------------------------------------------- | -------------------------------------------------------------- |
| 原生插件                         | 用插件市场的现成蓝牙插件                                       | 要花钱；要确认插件还在维护、且适配了 Android 12+ 的新权限      |
| plus.android / plus.ios 自己写   | 直接调 Android 的 `BluetoothGatt` / iOS 的 `CoreBluetooth` | 工作量最大，两端各一套，还要处理权限、配对、后台限制、连接参数 |
| 关键功能用原生写，uni-app 只做壳 | 相当于放弃 uni-app 的收益                                      | 不推荐                                                         |

**App 端额外要处理的权限**（`src/manifest.json` 的 `app-plus.distribute` 里已经预留好了）：

- Android 12+：`BLUETOOTH_SCAN`、`BLUETOOTH_CONNECT`
- Android 6~11：扫描必须有 `ACCESS_FINE_LOCATION`
- iOS：`NSBluetoothAlwaysUsageDescription`（不写会直接崩）

### 7.3 建议的顺序

先把**小程序端 + 设备固件**联调通。协议是最容易出问题的部分（字段名、字节序、分包、
中文编码），而这部分现在有 400 多条断言守着，改起来最便宜。
App 端等真正有需求时再做 —— 到那时只需要补一个适配器文件。
